# 0004: Text

Game text is Shift-JIS in `main.dat` and in `AdvSys.bnd` (FMG, see [0001](0001-initial-findings.md)). `scripts/scene_text.py` lists it through the engine's structures. `scripts/text_survey.py` counts all Shift-JIS strings by a scan. Both read the output of `scripts/maindat.py`. [0007](0007-adventure-player.md) lists the text limits of the authoring tool.

| | Additional I | Additional II |

| Pointer strings | 1,225 | 1,784 |

Chunks repeat item, spell and menu records. Additional I has 47,895 record names and 7,245 pointer strings before deduplication.

## Global table

The game data structure starts at file offset `0x130` (header `0x5C`). Its `+0x14` field points to the global text header (`0x204` in Additional I).

A text header (`ADVP_TEXTDATA_HEADER_ST`) is two u32 values: count, then a pointer to the offset table. Each table entry is a u32 file offset of a NUL-terminated string, or `0xFFFFFFFF`. Additional I has 2,000 entries; unused entries hold `テスト`. Examples:

| Index | Text |
|---|---|
| 1 | `特に変わったところはない` |
| 3 | `鍵がかかっている\r\nあけるには鍵が必要だ` |
| 4 | `はい` |
| 5 | `いいえ` |

## Chunks

A chunk is a block in the engine's block list. It holds scenes: rooms, the town, menus and minigames. Chunk 0 is `街・戦闘`, chunk 1 is `オープニング`, chunks 2–7 are casino games, and later chunks are dungeon floors such as `B12F　神殿　水部屋`.

All pointers inside a chunk are absolute `main.dat` file offsets. `0xFFFFFFFF` means none.

### Block header

| Offset | Field |
|---|---|
| `0x00` | Size |
| `0x04` | Chunk index |
| `0x0C` | Scene count (u16) |
| `0x10` | Pointer, use not known |
| `0x14` | Scene pointer list |
| `0x18` | Image table, 16-byte entries |
| `0x1C` | Image table index (u16) read at block load |
| `0x1E` | Flags (u8); bit 1 is tested at block load |
| `0x20` | Name, 0x20 bytes |
| `0x44` | File offset of the block's sound BND |
| `0x48` | Pointer to the event header |

### Scene

| Offset | Field |
|---|---|
| `0x04` | Scene ID |
| `0x10` | Command data |
| `0x14` | Image data |
| `0x18` | Text header |
| `0x1C` | Event header |

A scene's text header has the same layout as the global one.

| | Additional I | Additional II |
|---|---|---|
| Scenes | 17,079 | 15,569 |
| Text pointers (global and scene) | 7,615 | 9,074 |
| Non-empty | 7,578 | 9,037 |
| Unique | 1,888 | 2,491 |

`scripts/scene_text.py` lists every text pointer with its source, chunk, scene ID, index and site.

### Events and actions

An event header holds a count and a pointer to the event pointer list. An event has its ID (5000–5999 in block events) at `+0x38`, its action count at `+0x3A`, an action list pointer at `+0x3C` and the list size at `+0x40`.

An action is a u8 opcode, a u8 length (multiple of 4), two bytes, and arguments. Every event ends with opcode `0x5C`. [0007](0007-adventure-player.md) names the opcodes. `scripts/chunk_commands.py` walks all actions: 1,486,651 in Additional I and 1,329,075 in Additional II, with no errors. No action argument holds a text address.

### Pointer strings

NUL-terminated Shift-JIS, reached through a text header. Dialogue uses this form:

```text
「行くのは勝手だが、\r\n　死ぬなら深い層にしてくれ。\r\n　我々も死体を回収しなくて済む」
```

### Text IDs

Actions select text by ID:

| ID | Table |
|---|---|
| 0–2999 | Global text, index = ID |
| 3000–3999 | Scene text, index = ID − 3000 |

| Opcode | Action | Text ID fields |
|---|---|---|
| `0x29` | `PutTextToWnd` | u16 at `+0x4` |
| `0x64` | `CallDialog` | u16 at `+0xC` (question), u16 at `+0xE`–`+0x16` (up to five answers); 0 means unused |

`scripts/text_refs.py` resolves every ID reached from scenes. All resolve. An event reached from two scenes counts twice.

| | Additional I | Additional II |
|---|---|---|
| `0x29`, global | 9,856 | 9,525 |
| `0x29`, scene | 3,522 | 3,464 |
| `0x64`, global | 45,448 | 41,382 |
| `0x64`, scene | 4,801 | 4,738 |

## Names

Commands and flags are arrays of 0x20-byte records. The name comes first:

| Offset | Size | Field |
|---|---|---|
| `0x00` | 0x18 | Name, Shift-JIS, zero-padded |
| `0x18` | 2 | Not known |
| `0x1A` | 2 | Index in the list |
| `0x1C` | 4 | `0xFFFF`, `0xFFFFFFFF` or a link value (`0x0BBB` seen) |

The game data structure (file offset `0x130`) holds the global arrays:

| Offset | Field | Additional I |
|---|---|---|
| `+0x04` | Flag count | 3,434 |
| `+0x08` | Flag records | `0xE750` |
| `+0x0C` | Global command count | 12 |
| `+0x10` | Global command records | `0x29490` |
| `+0x14` | Global text header | `0x204` |
| `+0x1C` | Block list | `0x6B100` |

A scene holds its command count at `+0x0C` and its command records at `+0x10`. Command IDs follow the text ID ranges: below 3000 is global, 3000 and above is the scene array.

| | Additional I | Additional II |
|---|---|---|
| Global commands | 12 | 12 |
| Flags | 3,434 | 3,434 |
| Scene command records | 64,026 | 54,736 |
| Unique scene command names | 550 | 548 |

Global commands are movement and menu entries: `前進`, `右へ向く`, `左へ向く`, `振り向く`, `アイテムSC`, `ステータス`. Scene commands are menu entries, items, spells and shop lines. A shop line puts the price inside the name with space padding: `ヴォルカノンソード  8600`.

A flag record uses the same layout with different fields: `+0x19` holds item bits, and `+0x1C` holds the initial value (`賭け金` starts at 100).

Flag names reach the screen only through the item list. `FUN_000ADF24` (Additional I, `CAP_FlagMng::ResetItemList` in Adventure Player) adds a flag to the item list when bit 0 of `+0x19` is set; bit 1 keeps it listed at count 0. No flag in either game sets these bits. The item list is empty, and flag names such as `所持金（仮）` appear only on debug screens. Players see item names through scene command records.

## Markup

`FUN_00017278` (Additional I) parses `#` codes. Arguments are hex digits in brackets.

| Token | Meaning | Evidence |
|---|---|---|
| `\r\n` | Line break | |
| `　` (U+3000) after a break | Indent inside quoted speech | |
| `#c[rrggbb]` … `#c` | Text color on, off | Seen in text |
| `#a[aa]` … `#a` | Alpha on, off | Parser reads one byte |
| `#b` | Bold on or off | Parser toggles a flag |
| `#m[nn]` | Icon `nn` | Item lines start with `#m[7c]`–`#m[85]` |
| `#f[nnnn]` | Value of flag `nnnn` | Parser calls `CAP_FlagMng::GetFlagValue`; `所持金：#f[00d5]G` |
| `#e[sssspppppp]` | Sound effect `ssss` with three parameters | `#e[1411400000]` names ID 5137; ID 5137 is in 56 sound BNDs. Additional I only. |
| `#d`, `#g`, `#i`, `#p`, `#r`, `#s`, `#w`, `#z` | Parsed; not used in `main.dat` text | |

Item descriptions align columns with U+3000 spaces:

```text
#m[7d]水晶の瓶　　　　　　所持数 #f[0235]\n魔力を帯びた水晶で作られた器\n
```

## Line length

`scripts/scene_text.py` measures all scene and global text in half-width units. A full-width character counts 2; markup is excluded.

| | Longest line | 99th percentile | Most lines in one text | Longest text |
|---|---|---|---|---|
| Additional I | 52 | 46 | 6 | 204 bytes |
| Additional II | 56 | 46 | 7 | 149 bytes |

Most texts have one to three lines. The windows therefore hold at least 56 ASCII characters per line at the 8-pixel advance. The engine limit is not known.

## Tools

`kfa text export GAMEDIR OUT.json` writes one record per unique source string. `GAMEDIR` is an extracted `PSP_GAME` folder; the command reads `BOOT.BIN`, `main.dat` and the code tables in `AdvSys.bnd`.

| Field | Content |
|---|---|
| `ja` | Source text; line breaks as `\n` |
| `en` | Translation; empty means unchanged |
| `kind` | `text` (text header string), `name` (command record name), `menu` (system menu record name) or `flag` (flag record name) |
| `max` | Bytes available: the smallest source length among the slots |
| `count` | Number of slots that hold this source text |
| `where` | Up to five slot labels: `g` global, `cNNN/sNNNNN` chunk and scene, `tNNNN` text index, `nNNNN` name index |

Additional I: 3,692 entries (1,887 `text`, 1,234 `flag`, 562 `name`, 9 `menu`) from 75,102 slots.

Flag records: game data `+0x04` is the count (3,434) and `+0x08` points to 0x20-byte records. The name is at byte 0; bytes 0x0C to 0x1B are zero in both games, so the name field is 0x18 bytes. Bytes 0x1C to 0x1F hold the initial value. The status labels `体力`, `魔力` and `素早さ` are flag names, but the screen draws them from the HUD image ([0012](0012-images.md)). No flag name has been seen on screen.

System menu records: game data `+0xC0` is the menu item count (6) and `+0xC4` points to 0x20-byte records. The records continue up to the address at game data `+0x00` (15 records in both games). Bytes 0–2 hold IDs; the name field is 0x1D bytes from byte 3. Records 0–3 are the Start menu (`ロード`, `操作説明`, `環境設定`, `ゲーム終了`). Records 8–14 are controls lines.

`scripts/text_merge.py OLD.json NEW.json OUT.json` carries translations into a new export. `scripts/text_apply_tsv.py EXPORT.json IN.tsv TARGET.json` sets translations from `INDEX<TAB>ENGLISH` lines; `|` is a line break.

`kfa text import GAMEDIR IN.json OUT.dat [BASE.dat]` writes each translation into every slot with the same source text, fills the rest of the slot with zero bytes, re-encrypts the units and re-signs `main.dat`. A text string that does not fit moves to new space in its chunk ([Longer strings](#longer-strings)). A translation that does not encode, or a name that does not fit, is not written and is listed. Slots always come from the original `main.dat`: a slot's budget is the length of its original string. `BASE.dat` is the file to write into, for example the output of `kfa img import`.

Shift-JIS conversion uses the game's tables (`internal/sjis`): `jis2ucs.bin` and `ucs2jis.bin` map JIS X 0208 codes to UCS-2 and back. All 1,231 non-ASCII characters in the Additional I text convert both ways.

ASCII uses 1 byte per character and Japanese uses 2, so a translation has twice as many characters as the source has characters.

## Town test

The opening has no font text: the title, a loading screen, the opening movie ([0006](0006-movies.md)), then the town map.

The town is chunk 0: 476 entries (329 `text`, 147 `name`). `research/text/c000-en.tsv` translates 425 of them; the rest are placeholders (`テキスト1`, `貴重品13`). The import writes 19,369 slots in place, because the same strings repeat in other chunks.

A line break costs two bytes (`\r\n`). The same source text can have a smaller budget in another chunk.

## Longer strings

The engine never rewrites chunk pointers. Each access computes `buffer + pointer - chunk offset`, with the chunk offset from the chunk table. A chunk that moves in `main.dat` needs every pointer in it changed, and no table lists the pointer fields. A chunk must not be larger than 0x500000 bytes. Chunks are aligned to 0x800 bytes; the space between chunks is 0 to 2,032 bytes.

`kfa text import` keeps each chunk in place and makes space inside it:

1. A text string that does not fit its slot needs new space in its chunk.
2. The import re-encodes the chunk's largest JPEG at quality 80 (then 75). The disc JPEGs are about quality 85. The smaller file goes in place ([0012](0012-images.md)); the end of the old space is free.
3. The string goes into the free space. Every text table entry that points to the old string changes to the new address. The old slot is filled with zero bytes.

Only `text` strings can move: they are reached through text table pointers. `name`, `menu` and `flag` fields are fixed in their records.

The header unit has no JPEGs. Its strings go to the end of the HUD atlas pixel data ([0012](0012-images.md)): the atlas is 512 × 256 and swizzled, and tile bands 12 to 31 (rows 96 to 255) are empty. The import keeps one empty band as a margin and uses the rest, 155,648 bytes. The atlas is RGBA 5551: bit 7 of each high byte is the alpha bit. The game draws parts of those rows as transparent pixels, so a non-ASCII byte there shows on screen as a colored speck. The import puts only ASCII strings in the atlas; every pixel stays transparent.

Result for the town, shop and global text test: 503 strings moved, 11 JPEGs re-encoded, all strings written. In headless PPSSPP the tavern shows a moved line (`"Enjoy yourself while you can."`). The tavern background and the town map show no visible change.

In headless PPSSPP the tavern shows English: the greeting, the owner's lines, the menu (`Talk to the owner`, `Talk to a customer`, `Casino`) and the location title.

## Shop test

Chunk 8 holds the shop, the smithy and their lists. `research/text/items.tsv` maps 176 item and category names; the same names apply to global text. In headless PPSSPP the shop shows English: dialogue, the `Buy` and `Sell` menu, the categories, the item list with prices, the price panel image and the item description (a global string moved into the HUD atlas). The description box holds about 50 characters per line before the `Buy` and `Stop` box.

## Global text

Global text (`g/t`) holds system messages, area, enemy and person names, spell names and descriptions, casino labels and item descriptions. Source files in `research/text`:

| File | Content |
|---|---|
| `global1-en.tsv`, `global2-en.tsv` | Messages and names, by export index |
| `desc-ja.tsv`, `desc-en.tsv` | The 209 unique free-text description lines |
| `items.tsv` | Item and category names |

`scripts/text_center.py` centers English like a source that starts with spaces: the center column stays the same. `scripts/item_desc.py` builds item descriptions: the header line gets the English name padded to the Japanese column, `Dur`, `Arrows`, `Owned` and `Wt`; the stat line gets two-letter codes (`Cu Hi St Fi Ea Wi Wa Li Da`), one code for each full-width character, so the columns stay aligned.

The engine formats these strings with a `printf`-style function: an ASCII `%` and the characters after it do not show. The Japanese uses the full-width `％`. English text must not contain `%`.

In headless PPSSPP the shop shows a weapon description in English with aligned stats.

## Repacking

- A longer string moves the data after it. Every pointer to moved data needs an update.
- Pointers are absolute file offsets. A chunk that moves in `main.dat` needs all its internal pointers rebased. Strings that grow stay in their chunk ([Longer strings](#longer-strings)).
- `scripts/text_survey.py` finds pointers by scanning aligned u32 values. A data word can equal a string offset by chance: in chunk 0 of Additional I, a GIM palette color equals the address of a dialogue line. Use the text headers (`scripts/scene_text.py`) to locate pointers.
- Names have a fixed 24-byte field: 23 ASCII characters and a terminating zero.
